# Автономная смена на сервере: план и setup

Как оставить агента на сервере на двое суток решать большую задачу. Физическая
часть (tmux, сон, сервер, что где работает) — [`UNATTENDED_RUNS.md`](UNATTENDED_RUNS.md);
здесь — архитектура смены и что нужно решить до запуска.

## Главный вывод: не одна длинная сессия, а много коротких

Инстинктивное решение — запустить чат в tmux и дать ему работать двое суток —
ломается предсказуемо, и это описано теми, кто уже пробовал
([разбор типичных отказов](https://medium.com/@evekhm/running-claude-code-autonomously-overnight-what-breaks-and-how-to-fix-it-3bee3bd958b5)):

- **контекст переполняется**, срабатывает компактификация, и после нескольких
  сжатий инструкции теряют силу — агент через полтора-два часа начинает
  игнорировать правила, которые в начале выполнял;
- **агент не видит, сколько контекста осталось**, поэтому не может сам
  остановиться вовремя;
- **одна ошибка в середине** превращает остаток смены в мусор, потому что никто
  не проверяет промежуточный результат.

Рабочая архитектура — **оркестратор + фазы**: очередь задач, на каждую задачу
запускается отдельная сессия `claude -p` со **свежим контекстом**, а связь между
задачами идёт только через файлы и git. Тогда компактификация не наступает
вообще, а цена ошибки ограничена одной задачей.

```
scripts/night_shift.sh (в tmux, живёт двое суток)
   └─ берёт первый незакрытый пункт docs/NIGHT_QUEUE.md
      └─ claude -p "<задача>" --permission-mode bypassPermissions --max-turns N
         └─ агент: делает → тесты → коммит+пуш → WORKLOG → budget_log
      └─ проверяет, что HEAD сдвинулся и дерево чистое
      └─ отмечает [x] или [!] и берёт следующий
```

## Что уже готово в репозитории

| Файл | Роль |
| --- | --- |
| `scripts/night_shift.sh` | оркестратор смены |
| `docs/NIGHT_QUEUE.md` | очередь задач (`- [ ]` / `- [x]` / `- [!]`) |
| `scripts/night_shift_queue.py` | отметка результата в очереди |
| `.claude/hooks/guard-unattended.sh` | запреты, которые действуют даже без прав |
| `docs/WORKLOG.md` | состояние между задачами |
| `docs/BUDGET_LOG.md` | во что обошлась каждая задача |
| skill `slava-budget-pacing` | как расходовать лимит |
| skill `slava-long-sessions` | что писать на диск |

## Разрешения: единственное место, где нужен риск

Без человека некому подтверждать вызовы инструментов, поэтому сессии
запускаются с `--permission-mode bypassPermissions`. Это по определению снимает
защиту, и компенсируется двумя вещами.

**Хук-страж** (`PreToolUse`, работает независимо от режима прав) жёстко
запрещает то, что необратимо или нарушает договорённости: правку `task.md` и
замороженного пилота, `git push --force`, `git reset --hard`, удаление тега
`slava-pilot-v0`, удаление репозитория на HF и удаление `rollouts/final`.
Проверено на реальных payload'ах; обычные действия проходят молча.

**Git как страховка.** Всё остальное обратимо: каждая задача заканчивается
коммитом, любую можно откатить. Поэтому смена и разбита на единицы размером в
один коммит.

Чего в списке запретов сознательно нет: сетевых вызовов и установки пакетов —
на своём сервере это рабочие действия, а не угроза. Если сервер общий или на
нём есть чужие секреты — смену там запускать не надо вовсе.

## Как формулировать задачи очереди

Каждая строка — одна единица работы **с проверяемым результатом**. Агент один,
спросить не у кого, поэтому:

- ✅ «Заполнить `category_ru`/`canonical_name_ru` для новых raw_name в
  `object_lexicon.csv` по правилам skill `slava-object-lexicon`; валидатор
  зелёный»
- ✅ «Сгенерировать дашборд видимости для сцен `data/full_set/`, коммит»
- ❌ «Улучшить отчёт» — нечего проверить, нечем закончить
- ❌ «Решить, показывать ли GreenVLA-R0» — это ваше решение, не агента

Спорные развилки закрываются **до** отъезда: форма с вопросами, оставленная
ночью, никого не дождётся.

## Ограничение по объёму задачи

`--max-turns` (по умолчанию 120) — предохранитель от зацикливания на одной
задаче. Есть и `--max-budget-usd`, если хотите потолок в деньгах: `SLAVA_MAX_BUDGET=5`.
Задача, не уложившаяся в потолок, помечается `[!]` и не блокирует остальные.

## Что делать с лимитами

Смена на двое суток заведомо упрётся в 5-часовое окно. Оркестратор ловит это по
тексту ошибки, спит 30 минут и повторяет ту же задачу — то есть паузы штатны и
ничего не ломают. Внутри сессии агент действует по `slava-budget-pacing`:
ниже 15% остатка не начинает новое, а доводит текущее до коммита.

**Важно:** проценты лимита видны только при запуске в терминале (статуслайн),
поэтому на сервере запускать надо именно так, а не через IDE-расширение.

## Запуск

```bash
ssh user@server
tmux new -s slava
cd SLAVA_dev && git pull
# наполнить docs/NIGHT_QUEUE.md согласованными задачами
SLAVA_SHIFT_HOURS=48 bash scripts/night_shift.sh 2>&1 | tee -a rollouts/night_shift.log
# Ctrl+b d — отсоединиться
```

## Мониторинг, не приходя к серверу

Смена сама себя публикует: после каждой задачи идёт коммит и пуш, поэтому
прогресс виден из истории коммитов на GitHub с телефона. Подробности — в
`docs/WORKLOG.md`, стоимость — в `docs/BUDGET_LOG.md`, логи каждой сессии — в
`rollouts/night_shift/`.

## Чего этот setup не умеет

- **Принимать решения за вас.** Всё спорное превратится в `[!]` и будет ждать.
- **Работать с кадрами роллаутов** — 16 ГБ лежат только на ноутбуке.
- **Пережить перезагрузку сервера** — tmux этого не умеет. Если хостер может
  ребутнуть машину, отключите автообновления на время смены.
- **Гарантировать качество** — проверка автоматическая и грубая: тесты зелёные,
  HEAD сдвинулся, дерево чистое. Ревью утром за вами.

## Что решить перед первым запуском

1. **Задача смены** и разбиение на очередь — главное, и это делается вместе.
2. **Потолок**: `--max-turns` и нужен ли `--max-budget-usd`.
3. **Сервер**: где, есть ли на нём то, что нужно задачам (данные, окружения).
4. **Что считать успехом смены** — чтобы утром было с чем сравнить.

## Открытый вопрос: не проверено вживую

Оркестратор и хук-страж протестированы по частям (синтаксис, разметка очереди,
реальные payload'ы запретов), но **полный цикл с реальным `claude -p` ещё не
гонялся**. Перед двухсуточной сменой обязательно прогнать пробную: одна-две
маленькие задачи в очереди, `SLAVA_SHIFT_HOURS=1`, и посмотреть, что коммиты
появляются, а очередь отмечается.
